## What I Learned from Multi-Cloud Explorer

Laboratory 03 gave me the opportunity to look beyond just one cloud provider and compare **AWS, Microsoft Azure, and Google Cloud**.

I learned that although these platforms use different names for their services, they provide many similar solutions. For example, **Amazon EC2, Azure Virtual Machines, and Google Compute Engine** can all be used to host virtual machines.

I also learned that choosing a cloud platform depends on the needs of an organization. AWS offers a wide range of services, Azure works well with Microsoft technologies, and Google Cloud has strong capabilities in areas such as AI, machine learning, and Kubernetes.

Another part of the activity involved examining a Linux server using commands such as `lsb_release`, `lscpu`, `free`, and `df`. This helped me connect the Linux environment I was working with to actual cloud hosting services.

---

## What I Learned from Cloud-Native Engineer

Laboratory 04 introduced me to **Docker and containerization** and helped me understand how containers differ from traditional virtual machines.

I learned that containers are lightweight and can start much faster because they share the host operating system's kernel instead of requiring a separate guest operating system.

I also practiced basic Docker commands, including pulling an Nginx image, running a container, mapping ports, checking its status, stopping it, and removing it.

One of the activities I found useful was deploying an Nginx web server and accessing it through `http://localhost:8080`. This helped me understand how port mapping connects a port on the host to a port inside a container.

Overall, this laboratory gave me hands-on experience with containerized applications and helped me understand an important part of cloud-native computing.

---

## What I Learned from MinIO Object Storage Deployment

Laboratory 05 introduced me to **MinIO, an object storage solution that supports the Amazon S3 API**, and gave me more practice deploying services using Docker.

I learned how to run MinIO in a container and map ports `9000` and `9001` so I could access its services through the host machine. I also became more familiar with Docker options such as `-d`, `-p`, and `--name`, which helped me understand how to run a container in the background, expose ports, and assign a name to a container.

This activity helped me see how Docker can be used to deploy more than just web servers. It can also run storage services that organize and manage objects such as files and other data.

Although I still have more to learn about object storage and cloud infrastructure, this laboratory helped me become more comfortable with container deployment and gave me a better understanding of how storage services can be used in cloud environments.

---

## What I Learned from Cloud Deployment Engineer

Laboratory 06 helped me understand how Docker Compose can make application deployment easier. Instead of configuring Nextcloud and MariaDB separately, I used a `docker-compose.yml` file to define both services in one place.

I also learned how the two containers communicate with each other and why the `MYSQL_HOST` environment variable is important for connecting Nextcloud to MariaDB. Working with YAML gave me more practice writing configuration files and reminded me to be careful with indentation.

What I found useful about this activity was seeing how different services can work together to form one application. It helped me understand that cloud deployment is not just about running containers but also about configuring them properly so they can communicate.

I still have more to learn, but this laboratory gave me a better understanding of Docker Compose and how it can simplify the process of managing multi-container applications.

---

## What I Learned from Cloud Operations Engineer

Laboratory 07 helped me understand why monitoring is important even after an application has been deployed. I practiced checking the server's RAM, disk space, and CPU activity using Linux commands before monitoring my Nginx container.

I also learned how to use `curl` to send HTTP requests and simulate a 404 error by visiting a page that does not exist. Using `docker logs` helped me see the requests recorded by Nginx, while `docker stats` allowed me to check the container's CPU and memory usage in real time.

One thing I learned from this activity is that deploying an application is only part of the process. We also need to monitor its performance and check for errors to understand whether it is working properly. This laboratory gave me more practice troubleshooting basic problems and made me more familiar with the tools used to monitor containerized applications.

---

## What I Learned from Cloud Security Engineer

Laboratory 08 helped me understand that running an application is not enough; the server also needs to be protected. I deployed an Nginx container with Docker and used UFW (Uncomplicated Firewall) to control which incoming connections were allowed.

I practiced allowing SSH for remote administration, setting a Default Deny policy for incoming traffic, and opening TCP port 8080 for my web application. Checking the firewall rules and testing the Nginx page with `curl` helped me understand how these commands work in practice.

This activity also showed me why unnecessary open ports can be risky. A firewall adds another layer of protection, and allowing only the connections needed by the application helps reduce the server's attack surface. I still have more to learn about cloud security, but this laboratory gave me a better understanding of how basic firewall rules help protect a server.
